What needs attention

  • High
    Portainer is public on Server 2 (ports 9443 and 8000). Portainer controls Docker, which means root on the host. The AdGuard, wg-easy and homer web UIs are public too.
  • High
    Both 3x-ui panels are reachable from the internet. The odd port and random path only hide them. Scanners still find the port, and a bug in the login page would expose the whole server.
  • Medium
    No firewall policy you can point to, and no automatic security updates. Nothing written down says which ports should be open.
  • Medium
    No backups. If a provider loses a server, every client config and routing rule in x-ui.db is gone.
  • Medium
    Moscow WG users don't get AdGuard filtering. Only Server 2's own WG clients use it, through the Docker-local address.
  • Medium
    Docker runs on Server 1 with no containers, using RAM on the smallest server for nothing.
  • Medium
    Disks are 72 % (Server 1) and 86 % (Server 2) full, and Server 2 is already using swap.
  • Good
    SSH accepts keys only. Plain DNS no longer answers from outside (checked 2026-11-21). Moscow WireGuard users already run on Xray's own WireGuard inbounds.

Target architecture

The servers keep only the VPN and tiny agents. Everything heavy runs at home in Hyper-V and reaches the servers over a separate management WireGuard network. Admin access (SSH, panels, metrics) never touches the public internet.

Roadmap

Phases, in order

Each phase leaves the servers working. Don't start the next phase until the "done when" check passes.

  1. 0

    Inventory and safety net

    day 1Done
    • On both servers, save cat /etc/os-release, free -m, ss -tlnp, ss -ulnp into docs/inventory/. Remove IPs before anything goes public.
    • Copy to your PC: /etc/x-ui/x-ui.db, AdGuardHome.yaml, and the wg-easy data folder or volume.
    • Check that the provider's web console (VNC) works for both servers. That's your way back in if SSH breaks.
    • Take a provider snapshot if your plan has one.
    • From your PC, test port 53: Resolve-DnsName example.com -Server <IP> -DnsOnly.
    Done whenYou could restore every VPN client from files on your PC.
  2. 1

    Quick security fixes, by hand

    week 1Done
    • Update 3x-ui to the latest release on both servers.
    • Firewall with default deny (nftables or ufw). Allow only the ports in the table above, plus SSH for now.
    • AdGuard: set its DNS listener to 127.0.0.1 and the Docker bridge only. Turn on ClientIDs and "Allowed clients" for DoH.
    • Make sure wg-easy's web UI (usually tcp 51821) isn't reachable from outside.
    • unattended-upgrades on both. Add zram swap on Server 1.
    Done whennmap from home shows only the planned ports.PortfolioAdGuard open-resolver postmortem, plus before/after scan output.
  3. 2

    Home lab base and management network

    week 2Done
    • Turn on Hyper-V and create an external virtual switch.
    • VMs: vm-ctl (Debian 12, 2 GB), vm-mon (Debian 12, 2–3 GB), vm-staging (same OS as the VPSes, 512 MB to mimic Server 1).
    • Create a private Git repo. A cleaned public copy comes later.
    • Kernel WireGuard wg-mgmt on both servers. vm-ctl connects to both with PersistentKeepalive = 25 (home is behind NAT).
    Done whenFrom vm-ctl you can SSH to 10.99.0.11 and 10.99.0.12.
  4. 3

    Everything in Ansible

    weeks 3–4Done
    • Roles: common, hardening, firewall, wg_mgmt, xui, adguard, node_exporter, backup.
    • hardening: a sudo user, PermitRootLogin no, SSH listening on the mgmt IP only.
    • firewall: an nftables template generated from the port table in variables.
    • xui: installs a pinned 3x-ui version and restores x-ui.db from a backup.
    • Secrets (UUIDs, Reality keys, WG keys) go in Ansible Vault.
    • Run every role on vm-staging first, and only then on the real servers.
    The step that moves SSH and the panel to mgmt-only is the one most likely to lock you out. Do it with the provider console open and a second SSH session still connected.
    Done whenOne ansible-playbook site.yml turns a fresh staging VM into a working copy of Server 2.
  5. 4

    AdGuard for Moscow users

    week 4Done
    • Xray DNS module on Server 1, pointing at https://dns.yourdomain:3452/dns-query/srv1-moscow, with a hosts entry so the name resolves without DNS.
    • A routing rule sends the DNS module's own traffic through the vless outbound to Server 2.
    • A rule port 53 → dns-out for the WG inbound, placed above the geoip:private block.
    • If Russian sites get slow, send Russian domains to a local resolver as a split.
    Done whenQueries from a Moscow WG client show up in AdGuard's log as srv1-moscow, and ads are blocked.
  6. 5

    Retire wg-easy

    weeks 5–6Started
    • On staging, add a 3x-ui WireGuard inbound and benchmark it against wg-easy with iperf3: throughput, CPU, latency.
    • Server 2 first. Create the new peers, move users in batches, and keep wg-easy running as a rollback for one week.
    • Server 1 never had wg-easy (its users already use Xray's WireGuard inbounds), and its unused Docker was removed on 2026-11-22.
    • Write the runbook and the rollback steps as you go.
    If Xray's WireGuard turns out too slow on 1 vCPU, use plain kernel WireGuard managed by Ansible instead. Record the numbers and the decision in an ADR. It's a good interview story either way.
    Done whenDocker is gone from Server 1, every user is on the new setup, and the benchmark table is in docs/.
  7. 6

    Monitoring and alerts

    week 7Done
    • Prometheus on vm-mon scrapes node_exporter and Xray stats over the mgmt network.
    • Blackbox probes run from each server against a list of domains, so you can see what's reachable from Moscow versus Lithuania.
    • Grafana: one dashboard per server, traffic per hop, traffic per user.
    • Alertmanager → Telegram bot: server down, tunnel down, disk over 85%, memory over 90%, DoH certificate expiring.
    • Uptime Kuma status page published at status.yourdomain through a Cloudflare Tunnel. No open ports at home.
    Done whenStopping Xray on staging sends you a Telegram alert within 2 minutes.
  8. 7

    Backups and disaster recovery

    week 8Done
    • Nightly restic backup of x-ui.db, the AdGuard config and /etc/wireguard to home and to an offsite bucket, with a retention policy.
    • Restore test every month, on staging.
    • DR drill: reinstall Server 1 from the provider panel, run Ansible, restore, and time it. Record your screen.
    Done whenYou have a measured recovery time, e.g. "Server 1 rebuilt in 14 minutes".PortfolioThe DR video and the runbook.
  9. 8

    CI/CD for the infrastructure

    week 9Started
    • Gitea Actions on vm-ctl (or GitHub with a self-hosted runner inside the mgmt network).
    • On every pull request: yamllint, ansible-lint, Molecule tests, and ansible-playbook --check --diff.
    • On merge to main: apply to staging, then to production.
    Done whenA firewall change goes from pull request to both servers with no manual SSH.

    Extras, once the core is solid

    ongoingNot started

Ground rules

How not to lock yourself out

  1. Before any SSH or firewall change, keep a second session open and check that the provider console works.
  2. Every change runs on vm-staging first.
  3. Commit before you apply, so there's always a known-good version to go back to.
  4. Keep wg-easy running until the replacement has run for a week with no complaints.
  5. Secrets live only in Vault. The public repo has no real IPs, UUIDs, keys, domain or client names.
